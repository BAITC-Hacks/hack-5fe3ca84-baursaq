## 0. ЗАДАЧА (выбрана 23.09 — не пересматриваем)
Трек **Halyk Bank → Кейс 1 «Career Quest»** — AI-навигатор развития сотрудника.
ТЗ: `HACKATHON/*.docx` (лежит локально, в git не коммитим). Датасет: `data/career_quest/`
(схема — `data/career_quest/README.ru.md`).

**Что строим:** веб-приложение, где AI-слой по профилю, истории и требованиям следующего грейда
подбирает сотруднику 1–3 шага развития с объяснением, обновляет прогресс после прохождения
и даёт HR обзор отстающих компетенций.
**Ядро оценки — качество и объяснимость рекомендации, а не обёртка.** Геймификация — опционально.

### Must-have (так проверяет жюри)
1. **Профиль и траектория:** роль, грейд, навыки, пройденные активности, доступные следующие шаги.
2. **AI-рекомендация:** 1–3 релевантные активности.
3. **Объяснение:** опирается на ≥3 фактора — грейд, разрывы навыков, история участия, требования следующего уровня.
4. **Прогресс:** «отметить пройденным» → навыки и траектория сдвигаются.
5. **HR-вид:** какие навыки отстают чаще всего, у кого нет рекомендованного шага, участие по активностям.
6. **Загрузка** доп. профилей и истории в формате датасета. На защите жюри загружает 3 тестовых профиля,
   сделанных так, что однофакторное правило ошибается (пример: самый низкий навык Public Speaking, но человек
   3 раза пропускал похожие активности, а System Design критичен для следующего грейда).

### Запреты и ограничения
- НЕЛЬЗЯ: рекомендация по одному полю под видом AI; публичные рейтинги/лидерборды сотрудников;
  механики вокруг обязательных процессов (баллы за compliance, таймшиты); реальные ПДн.
- Приватность: данные вовлечённости не видны другим сотрудникам. Разделение прав employee / HR.
- Объяснимость: видно, почему предложен шаг и как считается прогресс.
- Запуск одной командой. Добровольность (принуждение — главный предиктор провала таких программ).
- Латентность: интерфейс ≤ 2 с, AI-рекомендация ≤ 10 с.

### Правила данных — ловушки, которые движок ОБЯЗАН учитывать
- «Сегодня» = `2026-10-01` (`meta.as_of_date`).
- Уровни навыков = последняя оценка. Мероприятия, завершённые ПОСЛЕ `last_review_date`, ещё не учтены →
  **эффективный уровень = оценка + их прирост** (таких записей 202; у E0028 из примера ТЗ EV_006 уже пройден →
  System Design = 3, а не 2).
- Прирост: `new = max(cur, min(cur + gain, max_level))`; если `cur ≥ max_level`, мероприятие ничего не даёт.
- Отсутствующий навык = 0. `mandatory` мероприятия НЕ рекомендуем. `completed` не повторяется (кроме `EV_036`).
- Пререквизиты проверяем по эффективным уровням. Сессионные форматы доступны, только если есть
  `upcoming_sessions` ≥ as_of; `self_paced` доступен всегда.
- Цель: `career_goal` (28 целей — это смена роли!), иначе следующий грейд своей роли; Lead без цели → свой профиль.
- `critical_skills` целевого грейда — ключ к повышению (вес ×2).
- История: `no_show` / `declined` / `dropped` по похожим (тот же навык / формат) → штраф; успешные завершения
  того же типа → бонус; `assigned_by=self` = внутренняя мотивация; remote-сотрудник + offline → штраф.

### Архитектура (зафиксирована)
```
React (frontend/) ──/api──> FastAPI (backend/app)
                              ├─ services/store.py   in-memory датасет (JSON/CSV), upsert при загрузке, reset
                              ├─ services/engine.py  детерминированный многофакторный скоринг + план 3 шагов
                              │                      с симуляцией прироста (эффективные навыки, цель, разрывы)
                              ├─ agents/recommender  LLM выбирает/переранжирует ТОЛЬКО кандидатов движка и пишет
                              │                      объяснение на языке сотрудника (kk/ru/en); таймаут → fallback
                              └─ services/hr.py      HR-аналитика
```
LLM не придумывает мероприятия и цифры: все факты и числа — из движка, LLM рассуждает и объясняет.

### API-контракт
Источник правды — `backend/app/models/api.py` (Swagger: http://localhost:8000/docs),
типы фронта — `frontend/src/api/types.ts`. Demo-auth заголовки: `X-Role: employee|hr`, `X-Employee-Id: E0028`.

| Метод | Путь | Доступ | Что возвращает |
|---|---|---|---|
| GET | `/api/health` | все | статус, размеры датасета, включён ли LLM |
| GET | `/api/catalog` | все | навыки, мероприятия, профили ролей, as_of |
| GET | `/api/employees?q=` | все | краткий справочник (вход / поиск) |
| GET | `/api/employees/{id}` | сам / HR | профиль: навыки (оценка / эффективный / требуемый), цель, готовность %, траектория, история, доступные шаги |
| POST | `/api/employees/{id}/recommendations` | сам / HR | 1–3 шага: rationale, factors, gains, readiness_after; rejected; trace |
| POST | `/api/employees/{id}/complete` | сам / HR | `{event_id}` → изменения навыков, готовность до/после, новый профиль |
| GET | `/api/hr/overview` | HR | отстающие навыки, у кого нет шага, участие по активностям, «выпадающие» |
| POST | `/api/dataset/upload` | HR | multipart `files`: employees.json / activity_history.csv / events.json / skills.json |
| POST | `/api/dataset/reset` | HR | вернуть исходный датасет |

## 9. ПРОДУКТ В ОДНОМ ЭКРАНЕ
ПРОБЛЕМА: сотрудник получает разрозненные HR-активности без связи с ростом → проходит формально,
добровольные активности пустуют, бюджет развития тратится впустую.
ПОЛЬЗОВАТЕЛЬ: сотрудник со стажем 1–5 лет (+ HR / руководитель).
МЕТРИКА ДЕМО: готовность к следующему грейду (%) растёт после шага; рекомендация учитывает ≥3 фактора
и обходит «ловушку» самого низкого навыка.
AGENTIC-МОМЕНТ: агент собирает профиль → считает эффективные навыки → разрывы к цели → паттерны истории →
кандидатов → планирует 3 шага с симуляцией прироста → объясняет на языке сотрудника; trace виден на экране.
СЦЕНАРИЙ ДЕМО (90 с): 1) боль HR одним предложением  2) профиль E0028: траектория Middle→Senior, готовность %
3) «Подобрать шаги» → trace + 3 шага с факторами и «почему не Public Speaking»  4) «Пройдено» → навык и % растут
5) HR-вид + загрузка тестового профиля на глазах у жюри.
ФРАЗА ПИТЧА: «Мы помогаем сотрудникам банка видеть, какой шаг приближает их к следующему грейду и почему,
а HR — где проседают компетенции, с помощью агента, который объясняет каждую рекомендацию по фактам».

## 10. MODEL ROUTING
- Основной: OpenAI (модель из `OPENAI_MODEL`, по умолчанию mini-класс — быстро и дёшево, укладываемся в 10 с).
- Fallback при лимитах/сбое: NVIDIA NIM (`https://integrate.api.nvidia.com/v1`, OpenAI-совместимо) — `FALLBACK_*` в `.env`.
- Последний рубеж: детерминированный движок с шаблонным объяснением (kk/ru/en) — демо не падает никогда.
- Казахский: объяснение генерирует флагман/mini OpenAI; если качество казахского критично — второй проход
  моделью-«редактором». Для фактов LLM опирается только на данные движка.
