## Подтверждённые находки

### P1 — JSON-импорт частично меняет исходные профили, затем падает с 500

Запрос: `POST /api/dataset/upload`, заголовок `X-Role: hr`, multipart-поле `files`, имя `employees.json`.
Взять полный исходный объект E0001, поменять `full_name` и загрузить:

```json
{"employees": ["<полный изменённый объект E0001, не строка>", null]}
```

Факт: HTTP 500; последующий GET E0001 уже содержит изменённое имя. Это не откат транзакции.
Отдельные минимальные входы `{"employees":[null]}`, `{"employees":["bad"]}` и `{"meta":[1]}` также возвращают 500.
Причина: запись прямо в store до проверки остальных элементов; обработчик ValidationError вызывает `item.get` у null/строки; тип meta не проверяется.
Код: `backend/app/services/store.py:77`, `:95`, `:157`, `:176`; обработчик исключений `:68` не ловит AttributeError.
Исправление: валидировать структуру и все изменения до применения; на невалидный элемент выдавать предупреждение без частичной записи.

### P1 — лишнее значение CSV вызывает 500 вместо предупреждения

Тот же endpoint, имя `activity_history.csv`:

```csv
record_id,employee_id,event_id,date,status,completion_pct
QA_RECORD,E0001,EV_005,2026-09-20,completed,100,EXTRA
```

Факт: HTTP 500. Когда значений больше заголовков, DictReader кладёт остаток в список под ключом None; код вызывает `.strip()` у списка.
Код: `backend/app/services/store.py:108`.
Лишние **именованные** колонки и пустая колонка заголовка с согласованной строкой проходят нормально.
Исправление: проверять переполнение строки и возвращать номер строки / понятное предупреждение.

### P1 — профиль с meta изменяет общий календарь всех сотрудников

Загрузить `employees.json` с `meta.as_of_date = "2030-01-01"` и одним новым профилем.
Факт: HTTP 200, warnings пусты; `/api/health.as_of` становится `2030-01-01`.
Ответы профилей E0001, E0028, E0072 изменились: доступность сессионных шагов рассчитывается уже по новой дате.
Это нарушает заданную дату демо 2026-10-01 и изоляцию добавочных профилей; UI при этом содержит фиксированную подпись «Данные на 1 октября 2026».
Код: `backend/app/services/store.py:79`–`:81`.
Исправление: не применять глобальную meta при добавлении профилей либо явно валидировать её и отделить замену всего датасета от добавочного импорта.

### P2 — повтор JSON с чужим record_id дублирует историю и прирост навыка

1. Создать QA001 как копию E0001 без истории.
2. Взять существующий `record_id` из истории E0001.
3. Дважды загрузить идентичный JSON:

```json
{"history":[{"record_id":"<record_id E0001>","employee_id":"QA001","event_id":"EV_005","date":"2026-10-01","status":"completed","completion_pct":100}]}
```

Факт: оба HTTP 200 без warnings; чужая запись сохранена, но у QA001 история растёт с 1 до 2. System Design растёт с 2 до 3 при повторе одного и того же файла. Готовность в этом примере остаётся 57%, поскольку целевое требование уже покрыто.
Код: `backend/app/services/store.py:166`–`:171`: при каждом конфликте выдаётся новый ID.
CSV с тем же конфликтом не повреждает чужую запись и при повторном импорте остаётся идемпотентным в проверенном примере.
Исправление: стабильно сопоставлять исходный ID + сотрудника, отклонять конфликт с предупреждением или дедуплицировать импортируемую запись.

### P2 — недостаточная валидация навыков и целей

```json
{"employee_id":"QA_VALIDATE","role":"Backend Engineer","grade":"Junior","skills":{"SK_PYTHON":-3}}
```

Факт: HTTP 200, warnings пусты; профиль возвращает readiness_pct **−12**.
Неизвестный `SK_UNKNOWN` также принимается без предупреждения. Несуществующий career_goal молча заменяется следующим грейдом.
Unknown Role без career_goal даёт предупреждение при импорте, но профиль сообщает **100% готовности** при отсутствии требований роли.
Код: `backend/app/models/dataset.py:44`, `backend/app/services/store.py:152`, `backend/app/services/engine.py:127`.
Исправление: валидировать диапазон 0–5, ссылки навыков/целей и не считать отсутствие профиля требований выполненной целью.

### P3 — текст пустого блока шагов предлагает повторить уже выполненное действие

Профиль QA_EMPTY: Lead, все навыки 5, career_goal=null. После «Подобрать шаги» основной блок правильно показывает «Подходящих шагов сейчас нет», но «Доступные шаги» по-прежнему предлагает нажать «Подобрать шаги».
Код: `frontend/src/pages/EmployeePage.tsx:96`.
Это не блокирует демо, но стоит согласовать пустые состояния.

## Что прошло

### Импорт

- Один профиль объектом, списком и `{"employees":[...]}`: 200; профиль открывается, рекомендации работают.
- Повтор этих файлов обновляет профиль без дубликата; загрузка employees.json не стирает его существующую историю.
- CSV с `;`, UTF-8 BOM, CRLF, пустыми optional-полями, дополнительными именованными и пустыми колонками: 200.
- Пустое обязательное числовое поле, неизвестный employee_id/event_id: понятное предупреждение, история не импортируется.
- Битый JSON и пустой файл: 200 с предупреждением, исходные данные не меняются.
- Коллизия record_id не перезаписала чужую запись ни в CSV, ни в JSON; отдельная проблема повторного JSON описана выше.
- Для обычных импортов сравнивались E0001/E0028/E0072. После reset все 200 исходных профилей совпали с базовым снимком.
- JSON-скаляр `42` молча игнорируется без предупреждения — дополнительный недостаток диагностики.

Ограничение: это demo-auth; роль и идентификатор задаются клиентом. Проверка не подтверждает реальную аутентификацию пользователя, которая исключена из scope проекта.

## Артефакты и воспроизведение

- `qa_probe.py` — основной HTTP-прогон; запуск Python из backend/.venv при работающем стенде 8012. Скрипт делает reset тестового in-memory датасета.
- `results.json` — полные ответы основного прогона.
- `extra_results.json` — частичная запись, двойной прирост и конкурентный complete.
- `validation.json` — отрицательный навык / неизвестная роль и грейд.
- `secrets.json` — обезличенный результат git-сканирования.

Перед защитой приоритет: P1 атомарность/500 → P1 дата датасета → P2 идемпотентность JSON → валидация уровней/ссылок.
